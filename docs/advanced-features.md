## Phase 1: warehouse access

Implemented in the current working tree:

- `UserWarehouse` holds multiple assignments and a preferred default. The old `User.warehouseId` stays synchronized as a compatibility default, but does not grant access by itself.
- Migration `20260930_warehouse_access` creates the assignment table, backfills existing non-null default assignments, and adds scope fields/indexes for notifications and audit logs. It contains no table drops or inventory resets.
- `warehouseAccessService.js` centralizes scope construction and resource checks. Administrator has unrestricted warehouse access; other users with no assignment have none.
- Authentication reloads database assignments on every authenticated request. Revocation therefore affects an already-issued access token on its next request.
- Bootstrap, warehouse detail/list endpoints, stock, movements, serials, purchasing/receiving, assets, maintenance, monitoring, dashboards, reports, and the existing loaded-data search source respect scope.
- Product/category/brand/supplier catalog metadata remains shared for authorized catalog/procurement users, so new products can be received. Stock balances, histories, order lists, valuations, and warehouse metrics are scoped. A warehouse filter must itself be authorized.
- Warehouse creation and user/role/access administration are administrator-only, in addition to the existing module permissions. Non-administrator user listings contain the requesting user's profile only.
- Users → Manage warehouse access supports multiple assignments and a default. New-user forms support the same fields.
- Warehouse selectors use the scoped backend result. Transfer source selections use assigned warehouses; a separate routing directory returns only destination identifiers, names, and codes.
- A transfer is visible to its source or destination. Create/edit/submit/approve/ship/cancel require source access; receiving requires destination access. Existing module action permissions are still required.
- Asset-owned serials remain visible through the asset's warehouse. In-transit serials are visible through the associated transfer's endpoints.
- Historical logs and notifications that cannot be assigned a warehouse confidently are retained for administrators and withheld from ordinary warehouse users. Exact order/receipt/transfer/asset references are backfilled. New warehouse operations record scope.

### API contracts

`PUT /api/users/:id/warehouses` requires Administrator and `users.EDIT`:

```json
{
  "warehouseIds": ["warehouse-a", "warehouse-b"],
  "defaultWarehouseId": "warehouse-a"
}
```

This replaces the assignment set transactionally. IDs must be unique, warehouses must exist and be active, and a supplied default must belong to the assignment set. Sending an empty set removes warehouse access. The user create/update contracts also accept `warehouseIds` and `defaultWarehouseId`; legacy `warehouseId` input remains supported.

`GET /api/transfers/destinations` requires `inventory.CREATE`. It returns `{ id, name, code }` records only, allowing a source user to request delivery to another warehouse without receiving access to that warehouse's inventory.

Unauthorized explicit warehouse filters, details, and actions return 403 using the existing error contract. An unfiltered list for an unassigned user is empty.

## Phase 2: physical stock counting

Inventory → Stock Counts supports creation, snapshot start, counting, review and approval. Serialized counts use one scanned serial per line, with expected/scanned/missing/unexpected sets. Page changes are blocked until edits are saved. Saved quantities lock on submission. Loading/empty/error/retry states use the existing UI. Scanner keyboard integration follows in the barcode feature.

Migration `20260930_z_stock_counts` adds count tables and enum values without removing existing data. ## Phase 3: reservations

Implemented warehouse-scoped reservation records, line quantities, fulfillment quantities, exact serial selections, optional expiry and project/deployment references. On-hand quantity stays unchanged when reserved; availability is on-hand minus reserved. Creation, release, cancel, fulfillment and expiry use serializable transactions, movement history and scoped audit records. Existing holds from earlier workflows are preserved.

Serialized reservations accept exact serials or select available units deterministically on the backend. Reserved units cannot be changed independently using the serial status endpoint. Fulfillment issues units from inventory, marks exact serials `ISSUED` and records their original warehouse/history. Partial fulfillment keeps the remaining hold active. Releasing or expiring a partial reservation releases only unfulfilled units. Fully fulfilled and closed reservations cannot be acted on twice. Fulfillment supplies `expectedFulfilledQuantity` per line to reject duplicate partial submissions.

`/api/reservations` supports paginated list/create/detail/items, scoped searchable availability, fulfill, release and cancel. Permission keys are `reservations.VIEW/CREATE/RELEASE/FULFILL`; Inventory Manager and Warehouse Staff receive all four, Viewer only VIEW. The role matrix uses backend module and action names, including nonstandard actions.

Inventory → Reservations provides create, backend warehouse availability, multiple items, optional exact serials, references and expiry; detail supports partial issue and remaining release. No frontend stock arithmetic is persisted. Relevant writes refresh the existing workspace projection; reservation lists/items are fetched independently.

Migration `20260930_zz_reservations` preserves existing stock and adds reservation tables, serial `ISSUED`, reservation movement types and nullable previous/new reserved quantities on movements. No old history is invented. A simple internal worker starts with the API and expires up to 100 due reservations each minute, processing each transaction separately. Expired holds conservatively remain reserved until the worker runs; fulfillment is immediately blocked after expiry. Multiple API workers remain safe through transactional state checks. The job status is operational memory; durable job administration follows later. Keep API clocks synchronized and run migrations before starting the API.

Verification: 44 tests pass across seven files using an isolated schema. Reservation coverage includes over-reservation, preserving other holds, partial/full issue, stale partial submissions, repeated close, expiry, exact/automatic serial selection, protected serial status, serial expiry, competing last-unit reservations, multi-item rollback, fulfillment races, input validation, permissions and warehouse scope. Ambiguous raw identifiers return multiple matches for explicit selection. Warehouse and module permissions apply to lookup and label payloads; payloads contain identifiers and label text only.

Product barcode generation requires products.EDIT, uses the authoritative reference counter, checks SKU/barcode collisions and locks the product row before allocation. Reusable focused serial inputs support stock counting, receiving, transfer packing/receiving and maintenance lookup. Transfer scans select exact available serials and receiving must match the shipped set; discrepancy handling follows in its own phase. Manual workflows remain available.

## Phase 7: RFQs and supplier quotations

Schema and migration `20261002_rfqs`, permissions, validators, services, controllers and routes are written. RFQs retain requested catalog/free-text item snapshots, invited suppliers, workflow timestamps, and a manual award with reviewer and selection notes. Draft supplier quotations record prices, specifications and terms; submitted offers are immutable. Comparison includes submitted offers without choosing a winner. Awarded quotation conversion creates a linked draft PO transactionally, preserving the PR → RFQ → quotation → PO relationships. The server calculates currency with decimal arithmetic. A purchase request with an active RFQ cannot also convert directly or cancel independently.

Frontend RFQ list/create/detail, quotation create/edit/detail, comparison, manual award and conversion dialogs are written and routed. Navigation is permission-aware. Approved requests link to their active RFQ or offer RFQ creation. Inventory Manager seed permissions match the RFQ migration.

### API and workflow contracts

`/api/rfqs` supports paginated list, create, detail and draft update; `/:id/issue`, `/close`, `/cancel`, `/comparison` and `/award` retain the document workflow. Permissions are `rfqs.VIEW/CREATE/EDIT/ISSUE/CLOSE/AWARD/CONVERT`; cancellation and quotation recording/submission require EDIT. Quotation endpoints are `/:id/quotations`, `/:quotationId`, `/submit`, `/cancel` and `/convert`. Conversion requires both `rfqs.CONVERT` and `purchasing.CREATE`. Every document read and write enforces the RFQ warehouse; access revocation applies to the next request with an existing token.

RFQs created from approved PRs use server snapshots of the approved line identities, quantities and descriptions. One active RFQ round blocks direct source-PR conversion and cancellation. Issue rechecks the source request and active invited suppliers. Quotation entry stops after closure or the closing deadline. Each supplier has one retained quotation per round; every requested line must appear once. Quantities and decimal totals are authoritative on the server. Submission rechecks that the supplier remains active and invited, even if it changed after draft creation. Submitted offers cannot be edited.

Updates, transitions, award and conversion require `expectedUpdatedAt`. Stale documents return 409. RFQ and quotation writes always advance their millisecond version tokens, including fast writes or a clock adjustment backwards; the regression suite checks old forms remain stale. Closing enables manual award of a submitted, unexpired offer, with reviewer, time and reason. Comparison does not rank or award automatically, and selecting a more expensive offer is allowed. Award creates no PO. A separate confirmed conversion maps every free-text line to a distinct active catalog product, preserves quoted quantities/prices/tax/shipping, and saves PR → RFQ → quotation → one DRAFT PO in the same serializable transaction. Cancellation retains the round, lines, invitations and quotations; converted rounds cannot be cancelled. No procurement step changes stock before receiving.

RFQ forms now display specific backend validation messages and preserve form values after rejection. PO detail shows two-decimal prices, authoritative line subtotals and the subtotal/tax/shipping/total breakdown.

## Phase 8: supplier returns / RTV — verified

Supplier returns are a separate document workflow under Procurement → Supplier Returns. Existing business rows are retained; no stock backfill, table reset or destructive migration is used.

### Workflow and inventory contracts

- DRAFT → PENDING → APPROVED → SHIPPED → COMPLETED. Cancellation is retained from DRAFT/PENDING/APPROVED only. Submitted lines are immutable. Completion records supplier acknowledgement/credit outcome as text; it does not post accounting entries or receive replacement stock.
- Each document has one recorded purchase receipt. Supplier, PO, warehouse and products are derived from that receipt on the server, never trusted from submitted identifiers. Each selected receipt line appears once; positive quantities cannot exceed received quantities after subtracting other pending, approved, shipped or completed returns. Drafts do not own quantities or serials, so competing drafts can exist but only valid claims can submit.
- Serialized lines require exactly one distinct selected identity per unit, matching the exact receipt, PO line, supplier, product and warehouse. Eligible states are AVAILABLE, DEFECTIVE or FOR_REPAIR with no asset ownership or ongoing maintenance. Legacy units without reliable receipt provenance cannot be returned through guessed receipt links.
- Draft save/edit changes no stock. Submission revalidates receipt claims and current serial availability, holds stock at the warehouse and changes selected serials to RETURN_PENDING. The existing reservedQuantity contract includes all unavailable units; already defective/repair serials are not held twice. Return lines retain how many additional units they held and each serial's actual pre-submission state.
- Cancellation releases only the return's new holds and restores each serial's exact previous state. Generic serial status changes, stock issues, reservations and asset/transfer selection cannot consume held return serials. Stock counts retain RETURN_PENDING units in their physical snapshot.
- APPROVE changes the document only. SHIP requires an explicit physical shipment reference: total and unavailable stock both decrease by the returned quantities, one movement is written per line, serials become RETURNED with no warehouse, and exact serial events/audit history remain linked to the return. No stock is silently removed by saving, submission or approval. SHIPPED/COMPLETED records cannot be cancelled or shipped again.
- Serializable transactions, balance guards and strictly advancing document versions protect receipt claims, draft edits, submission, shipment and cancellation races. Updates/actions require expectedUpdatedAt and return 409 for stale state. Every failure rolls back the complete document operation.
- Observed item condition is descriptive in this phase. Separate nonserialized defective/quarantine buckets are Phase 9 work; product status is not overloaded.

## Phase 9: defective/quarantine inventory — complete for development acceptance

### Balances and business rules

- WarehouseStock now has quarantineQuantity, defectiveQuantity, forRepairQuantity and returnPendingQuantity. They are classified subsets of the existing aggregate reservedQuantity. Physical quantity remains unchanged during classification; available = quantity − reservedQuantity, and other holds = reservedQuantity − classified conditions. Existing reservations and unknown legacy holds remain intact.
- Explicit changes support AVAILABLE, QUARANTINE, DEFECTIVE and FOR_REPAIR. Clearing stock requires a reason/inspection result. Product status is separate. RETURN_PENDING is controlled by supplier-return documents, and reservation holds cannot be released through the condition form. For-repair inventory is a stock bucket; preventive maintenance and warranty-claim workflows remain future phases.
- Each operation requires an exact warehouse/product balance version and positive source quantity. Serialized products require exactly one eligible serial per changed unit, in the source condition and warehouse; asset/active-maintenance units are excluded. Nonserialized products reject serial selections. Archived products and inactive warehouses are blocked.
- Serializable transactions write one zero-quantity CONDITION_CHANGED movement, immutable before/after balance snapshots, exact serial selections, lifecycle events and a scoped audit record. Physical totals are conserved. Guarded balance updates and strictly advancing timestamps reject stale forms, round trips, backward-clock stale versions and competing requests, and invalidate existing stock-count snapshots even for held-to-held changes.
- Issues, adjustments, reservations, asset creation and transfers continue to consume only available inventory. Generic serial status changes maintain classified balances and cannot bypass actual reservation or return holds.
- Quantity-tracked supplier-return lines now choose a source stockCondition independently of descriptive observed condition. Submission moves that source into RETURN_PENDING, adding unavailable quantity only for previously AVAILABLE units. Cancellation restores the source bucket; shipment removes pending physical/unavailable quantity exactly once. Serialized returns derive the source from each exact serial, including QUARANTINE, and restore it on cancellation.

### API, migration and frontend

GET /api/inventory/conditions lists paginated scoped warehouse/SKU balances, with search and held-condition filters. GET /serials provides scoped paginated eligible source serials; GET /history provides saved snapshots, reasons, users and selections. ## Phase 10: transfer discrepancies — complete for development acceptance

### Arrival accounting and investigation

- Shipping still removes only available source inventory. Exact serial selections exclude assets, active maintenance and actual reservations. Quarantine, defect, repair and return holds retain their owning workflow. No stock is added merely because a transfer was shipped or a shortage was reported.
- Each explicit arrival records good and damaged quantities separately, validates exact remaining shipped identities, and retains an immutable TRC document with receiver/time, notes, item/serial identities and stock movements. Good arrivals enter AVAILABLE; damaged arrivals enter destination QUARANTINE with one aggregate unavailable hold. Mixed and partial receipts are supported. Purchase receipt, PO item, supplier and warranty links remain unchanged.
- A final-arrival action closes ordinary receiving and creates MISSING cases for every outstanding serialized identity or nonserialized quantity. UNEXPECTED observations identify a related transfer line and observed serial/quantity, but never create serials, change ownership or add stock. Already-shipped identities cannot be classified as unexpected. DAMAGED cases identify the exact quarantined arrival.
- Retained investigation notes have actor/time and zero resolved quantity. Each explicit resolution appends a separate record with action, quantity, evidence and actor. Nonserialized shortages can be resolved in parts. MISSING supports physically recovered destination units (explicit AVAILABLE or default QUARANTINE), confirmed loss, or physical return to source QUARANTINE. Loss never subtracts stock again. Source returns require access to both warehouses. Exact serialized recovery/loss rejects identities no longer in transit, asset ownership, maintenance and reservation claims.
- DAMAGED acknowledgement resolves the investigation while retaining its stock hold. An inspected condition change remains a separate Stock Conditions operation. UNEXPECTED supports documented return/disposition without touching inventory. Quantity resolutions cannot exceed the unresolved case balance; resolved records cannot be repeated or cancelled away.
- PARTIAL means outstanding shipped units remain without open cases; DISCREPANCY means at least one case is unresolved. RECEIVED means every shipped unit arrived and every case closed. RESOLVED means all quantities are accounted for and cases closed, with some units confirmed lost or physically returned to source. Per-line shipped = received + lost + returned + outstanding. A retained case can therefore finish while stock still needs quarantine inspection.
- Serializable transactions, guarded document/case versions and strictly advancing timestamps prevent stale forms, duplicate arrival/recovery and competing outcomes. Writes include stock movements where physical quantities change, serial events and warehouse-scoped audit records. Database CHECK constraints guard line/case accounting and outcome/action values.
